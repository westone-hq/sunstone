# Sunstone 주석·코드 규칙

OTIS 주석 규칙(v4)을 Sunstone에 맞게 고친 것이다. 작업을 시작하기 전에 매번 다시 읽는다.
대상: `routines/` · `app/` 전체 (Kotlin). `tools/api-explorer`(Pleos 공식 샘플)는 제외한다.

OTIS와 달라진 점
- Kotlin만 쓴다. Dart 전용 규칙(`///`, 위젯 트리)은 Kotlin KDoc(`/** */`)과 Compose 트리로 바꿨다.
- 근거에 차량 실측 표기를 더했다. Pleos API는 문서와 에뮬레이터 동작이 다를 수 있어서, 실측 여부를 꼭 남긴다.
- 테스트·데모 우회로 규칙을 이 프로젝트 구조에 맞췄다(7장).

---

## 0. 파일 머리

아무것도 두지 않는다. 작성 이력은 선언 주석이, 변경 이력은 git이 갖는다.
`package` 위에는 라이선스·자동생성 표시처럼 도구가 요구하는 줄만 둔다.

---

## 1. 함수 · 클래스 · 상수 선언 주석

라벨 순서는 항상 같다. 해당 없는 줄은 뺀다.

```
작성 → 수정 → 함수/클래스/변수 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현
```

```kotlin
/**
 * 작성: 2026-11-08 21:10:00 · 박건준
 * 수정: 2026-11-09 10:02:11 · 박건준
 * 함수: runControl
 * 목적: 제어 단계 하나를 처리한다. 원래 값을 읽어 두고, 실행한 뒤,
 *       실패하면 그 단계만 음성 안내로 바꾼다.
 * 인자: run — 지금 실행 중인 루틴의 기록
 *       index — 처리할 단계 번호 (0부터)
 *       step — 처리할 제어 단계
 * 반환: 없음. 성공하면 되돌리기 목록에 원래 값을 더한다
 * 근거: 측정 — 에뮬레이터에서 창문 잠금은 읽은 값만 바뀌고 콘솔은 그대로였다
 *       (docs/api-spike.md 차일드락 행)
 */
```

### 1-1. 작성 · 수정

| 항목 | 형식 | 규칙 |
|---|---|---|
| 작성 | `작성: YYYY-MM-DD HH:MM:SS · 이름` | 초 단위까지 |
| 수정 | `수정: YYYY-MM-DD HH:MM:SS · 이름` | 그 선언의 내용이나 주석이 실제로 바뀐 경우만. 최신 1줄만 남긴다. 작성자와 같아도 남긴다 |

- 이름: 그 코드를 맡은 사람. 앱 연결(`app/`)은 **`박건준`**, 기능 구현(`routines/`)은 **`박희정`**.
  남의 영역 코드를 고치면 `작성:`은 두고 `수정:`에 자기 이름을 적는다.
- 값을 모르면 줄을 통째로 뺀다. `미상` 같은 채움값을 쓰지 않는다.

### 1-2. 첫 라벨

| 대상 | 라벨 |
|---|---|
| 함수 · 메서드 · 생성자 · 프로퍼티 getter · `@Composable` 함수 | `함수: 이름` |
| 클래스 · `object` · `interface` · `enum` · `sealed` 계층 | `클래스: 이름` |
| `const val` · `companion object` 상수 · 최상위 설정 상수 | `변수: 이름` |
| `when` 분기 하나가 요청 하나를 처리할 때(데모 명령, Gleo 함수) | `함수: 그 요청 이름` |

- `sealed interface` 안의 `data class`·`data object`도 각자 `클래스:` 를 갖는다.
- 라벨을 쓰기 시작했으면 첫 라벨이 반드시 있어야 한다. `목적:`만 있는 블록은 금지.

### 1-3. 필수 여부

| 항목 | 필수 | 기준 |
|---|---|---|
| 작성 | ✅ | 아는 경우 |
| 수정 | 바뀐 경우만 | |
| 함수/클래스/변수 | ✅ | 이름 그대로 |
| 목적 | ✅ | 무엇을 · 왜. 하는 일이 여럿이면 항목으로 |
| 인자 | 있으면 | `이름 — 설명(단위·범위·null 의미)` |
| 반환 | 있으면 | 의미(단위) + 실패·부작용 |
| 식 | 있으면 | 원래 기호 그대로 + 코드 변수 대응 (예: 주유 판단, 시트 허용 오차) |
| 근거 | 판단이 들어간 곳만 | 5장 |
| 미구현 | 미구현이면 | 6장 |

- `override`, `private` 포함 전부. 한 줄 getter·인자 없는 생성자는 `작성` + `함수` + `목적` 세 줄.

### 1-4. 줄바꿈과 들여쓰기

주석 줄은 80자, 코드 줄은 120자. 넘으면 줄을 바꾸고 다음 줄은 라벨 자리만큼 띄운다.

| 라벨 | 이어지는 줄 들여쓰기 |
|---|---|
| `작성` `수정` `함수` `클래스` `변수` `목적` `인자` `반환` `근거` `미구현` `미확인` | ` * ` 뒤 7칸 |
| `식` | ` * ` 뒤 5칸 |
| `목적` 안 불릿 | `- `를 7칸에서 시작, 넘치면 9칸 |
| `목적` 안 번호 목록 | `1. `을 7칸에서 시작, 넘치면 10칸 |

### 1-5. `목적:` 쓰는 법

- 첫 줄은 한 문장 요약. 필요하면 제약을 이어 쓴다.
- 하는 일이 여럿이면 `` - `식별자` — 설명 `` 불릿, 순서가 있으면 번호 목록.

## 2. 변수 주석

### 2-1. 상수 — 라벨 블록

`const val`, `companion object` 상수는 라벨 블록. 값의 이유가 중요하므로 `근거:`를 거의 항상 쓴다.

```kotlin
/**
 * 작성: 2026-11-08 21:10:00 · 박건준
 * 변수: LEAVE_SPEED_KMH
 * 목적: 세차장을 떠났다고 보는 속도 (km/h). 이 속도 이상이면 되돌린다.
 * 근거: 미정 — 세차장 안 이동(5km/h 안팎)과 구분하려고 임시로 정했다.
 *       시연 리허설 후 다시 정한다
 */
const val LEAVE_SPEED_KMH = 10f
```

같은 성격 상수가 무리로 있으면(창문·좌석 영역 대응표 등) 묶음 앞에 블록 한 번, 항목은 한 줄 주석.

### 2-2. 인스턴스 필드 — 라벨 없는 산문

```kotlin
/** 루틴을 시작한 순간의 차 상태. 자동 되돌리기 조건을 비교할 때 쓴다 */
val start: CarState
```

누가 채우고 누가 비우는지, null이면 무슨 뜻인지까지 적는다. `변수:` 라벨 금지.

### 2-3. 지역변수 — 뒤에 `//`

```kotlin
val before = runCatching { car.read(target) }.getOrNull() // 바꾸기 전 값, 못 읽으면 null
```

전부 단다. 80자를 넘기면 `=` 뒤에서 줄을 바꾸고 주석은 `=` 옆에 둔다.

### 2-4. Compose 트리 — 여는 괄호 다음 줄

```kotlin
Column(
    // 화면 전체: 상태 줄, 권하기 카드, 루틴 카드, 입력칸 순서
    Modifier.fillMaxSize(),
) {
```

글자로 이미 알 수 있는 것은 달지 않는다.

### 2-5. 공통

- 단위·범위·특수값을 적는다 (`km/h`, `0=닫힘~10=열림`, `null 이면 읽을 수 없음`).
- 시간은 우리말(`밀리초`, `초`). 변수 이름이 `Ms`로 끝나도 설명은 `(밀리초)`.

## 3. 로직 이동 표시

흐름이 다른 클래스·함수로 넘어가는 곳에 단다. 시퀀스 다이어그램의 근거다.

```kotlin
// → 로직 이동: RoutineRunner.request()
runner.request(action.request)

speaker.say(text) // → 로직 이동: Speaker.say()
```

- 대상 이름만. 함수는 `()`를 붙이고, 함수가 아닌 대상은 이름만.
- 호출부마다 하나씩. 실제로 도달하는 곳에만.
- 이 프로젝트에서 특히 꼭 다는 곳: ① 기능 구현 ↔ ② 앱 연결 경계(`CarPort`, `Speaker`, `SeatProfiles` 호출),
  `AppGraph.handle()` 진입, 데모·Gleo 입력이 루틴으로 들어가는 곳.

## 4. 말투

- 본문 주석은 "왜"만. 코드 반복 금지.
- 한국어 평서형(`~한다`). 영어는 식별자·단위·고유명사만.
- 코드 이름은 백틱으로 감싼다. 파일은 `차 연결(PleosCarPort.kt)`처럼 실제 파일명을 적는다.
- 먼저 쉬운 말로 풀어 쓴다. `suspend` → `비동기`, `StateFlow` → `값이 바뀌면 알려주는 상태`.
- 꼭 써야 하는 용어는 파일에서 처음 나올 때만 괄호로 푼다: `` `CarPort`(기능 구현이 차에 요청하는 창구) ``.

## 5. 근거 인용

`근거: 종류 — 내용`. 종류는 다섯이다.

| 종류 | 뜻 | Sunstone 예 |
|---|---|---|
| `표준` | 공개 표준·API 계약 | `표준 — Pleos Vehicle SDK 2.3.2 selectSeatMemory(area, value, onFailed)` |
| `인용` | 참조 자료에서 가져옴 | `인용 — 현대 오너스 매뉴얼 2027 중립 주차: 시동 끈 뒤 3분 안에만 N↔P` |
| `측정` | 우리가 직접 잼 | `측정 — Pleos 에뮬레이터 v2.1.0, 창문 0 설정 후 1.5초 뒤 읽은 값 0` |
| `미정` | 정하지 않아 임시 | `미정 — 세차장 반경 100m, 시연 후 조정` |
| `미확인` | 확인할 근거가 없음 | `미확인 — setWiperSwitch 서명은 문서 접근 전이라 이름으로 호출` |

- 실측 결과는 `docs/api-spike.md`에 표로 남기고, 코드에는 그 행을 가리킨다.
- 다른 팀 실측을 가져왔으면 `인용 — 길눈 팀 README(2026-11)`처럼 출처를 쓴다.
- 결정 코드만 던지지 않는다. 내용을 풀어 쓴다.

## 6. 미구현 표기

예외를 던지거나, 값을 흉내만 내거나, 빈 본문인 선언에는 `미구현:`을 붙인다.
무엇이 없는지 + 대신 무슨 일이 일어나는지를 부르는 쪽까지 따라가서 쓴다.

```kotlin
/**
 * ...
 * 미구현: Pleos 뒷유리 블라인드 API 서명이 확인되지 않아 이름으로 찾아
 *       부른다. 없으면 `ControlResult.Unsupported`를 돌려주고,
 *       `RoutineRunner.runControl()`이 그 단계를 "블라인드를 올려
 *       주세요" 안내로 바꾼다.
 */
```

- 고정 응답(키 없을 때 바깥 API 대신 쓰는 값)도 `미구현:`으로 밝힌다. 조용히 성공한 척하는 것이 가장 위험하다.
- 시연을 위해 실제 값 대신 넣거나 에뮬레이터 때문에 우회한 것은 `미구현:`에 "프로토타입이라"로 시작해 이유와
  실제 차에서는 어떻게 될지를 쓴다.

```kotlin
/**
 * ...
 * 미구현: 프로토타입이라 에뮬레이터에서만 탑승 값을 뒤집는다. 실제 차에서는
 *       SDK 값을 그대로 쓴다(실차 미확인).
 */
```

## 8. 링크

저장소를 GitHub에 올린 뒤부터 적용한다.
- 시작 줄 = 주석 첫 줄(`작성:`), 끝 줄 = 선언 닫는 괄호: `.../blob/<커밋>/<경로>#L<시작>-L<끝>`
- 주석 작업이 끝나면 전면 재링크, 커밋 해시 최신화. 인용한 줄번호는 실제 코드와 대조한다.

## 9. 점검표

1. 파일 머리에 작성 이력이 없는가
2. 선언 주석이 `작성 → 수정 → 라벨 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현` 순서인가
3. 함수·클래스·생성자·상수에 `작성:`이 빠진 곳은 없는가
4. `목적:`만 있고 첫 라벨이 없는 블록은 없는가
5. 이어지는 줄이 7칸(`식` 5칸, 불릿 9칸, 번호 10칸)인가
6. 인스턴스 필드에 `변수:`를 붙이지 않았는가
7. 계산식이 있는 함수에 `식:`이 있는가
8. 필드·지역변수에 단위·범위·설명이 있는가
9. 미구현·고정 응답에 `미구현:`이 있고 부르는 쪽까지 적었는가
10. 죽은 코드·부르는 곳 없는 선언이 없는가
11. 본문 주석이 "왜"만 말하는가
12. 주석 80자, 코드 120자를 넘지 않는가
13. 코드 이름을 백틱으로 감쌌는가
14. 용어 첫 등장에 풀이가 있는가
15. 근거가 `표준 / 인용 / 측정 / 미정 / 미확인`으로 시작하는가
16. Pleos API 호출마다 실측 여부(`측정` 또는 `미확인`)가 있는가
17. `로직 이동`이 호출부마다, 대상만 짧게, 함수에 `()`가 있는가
18. 데모·테스트 우회가 `src/debug/`와 조립부 밖으로 새지 않았는가
19. 10장(코드 스타일)을 어긴 곳이 없는가

## 10. 코드 스타일

두 사람이 쓴 코드가 한 사람이 쓴 것처럼 읽히게 한다.

### 10-1. 쓰지 않는다

| 하지 않는 것 | 대신 |
|---|---|
| 이모지·장식 기호(✅ 🗣 ⏳ 🚀 ★ ▶)를 코드·로그·화면·문서에 | 글자(`완료`, `안내`, `진행`, `건너뜀`) |
| 코드를 그대로 읽어 주는 주석(`// 리스트를 만든다`) | 주석 없이, 또는 "왜"만 |
| 섹션 구분 주석(`// ===== Helpers =====`, `// region`) | 파일을 나눈다 |
| 맞장구·홍보 말투(`깔끔하게`, `강력한`, `완벽히`, `간단히`) | 사실만 |
| `Manager`, `Helper`, `Util`, `Handler` 같은 뜻 없는 이름 | 하는 일 이름(`SeatMover`, `FuelAdvisor`) |
| 쓰지 않는 인자·기본값·확장 지점 "나중을 위해" | 지금 필요한 것만 |
| 모든 곳에 `try/catch` + 로그만 찍고 삼키기 | 실패가 의미 있는 곳에서만 잡고, 잡으면 처리한다 |
| 같은 내용을 KDoc과 본문 주석에 두 번 | 한 번 |
| 주석 처리한 코드 | 지운다. 기록은 git에 |

### 10-2. 지킨다

- 이름은 `docs/STRUCTURE.md` 6장 용어표를 따른다. 같은 것을 두 이름으로 부르지 않는다.
- 한 파일 안의 순서: 상수 → 생성자 인자·필드 → 공개 함수 → 내부 함수. 파일마다 같게.
- 로그 태그는 `SunstoneCar`, `SunstoneVoice`, `SunstoneDemo`, `Sunstone` 넷만.
  메시지는 짧은 한국어 또는 값만(`창문 닫기 실패: FL code=3`).
- 화면·음성 문장은 문장 틀 한곳에만 둔다. 코드 곳곳에 문자열을 흩지 않는다.
- 커밋은 작게, 한 주제씩.

### 10-3. 커밋 메시지

```
루틴: 세차 모드 와이퍼 단계 추가

와이퍼가 AUTO면 세차 중 움직여서 끈다. 되돌리기 때 원래 값으로.
```
- 첫 줄: `영역: 무엇을` 50자 안. 영역은 `루틴`, `엔진`, `말`, `대화`, `차`, `내비`, `정보`, `화면`,
  `데모`, `문서`, `빌드`.
- 본문: 왜 바꿨는지. 무엇을 바꿨는지는 diff가 말한다.
- 마침표·이모지·영어 접두어(`feat:`, `fix:`) 쓰지 않는다.
- `Co-Authored-By` 같은 꼬리 줄을 넣지 않는다.
- 커밋 작성자는 실제로 맡은 사람(`박건준` 또는 `박희정`) 계정으로 한다.
